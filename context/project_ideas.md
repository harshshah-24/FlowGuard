**Course:** 4CS501CC25 Principles of Compiler Design

**Assignment:** Innovative Assignment

## Purpose

Choose a practical compiler-design project that demonstrates understanding of core computer science. Each idea must produce a working prototype, source code, and documentation. The main contribution should be the implementation of fundamental algorithms, supported by correctness tests and measured results.

This document contains topic proposals. It is not an implementation plan. Language rules, implementation language, interfaces, and exact algorithms must be fixed in a separate approved plan after topic selection.

## 1. Small Compiler and Virtual Machine

### Project idea

Design a small, statically typed programming language. Compile programs into bytecode and execute that bytecode on a virtual machine you build.

### Fundamentals to implement

- **Lexical analysis:** Convert source text into tokens such as identifiers, numbers, operators, and keywords.
- **Parsing:** Check grammatical structure and build an abstract syntax tree.
- **Symbol tables and scope:** Track declarations and distinguish local variables from variables in enclosing scopes.
- **Semantic analysis:** Check types, declarations, function arguments, and return values.
- **Code generation:** Translate the syntax tree into bytecode instructions.
- **Runtime execution:** Implement an operand stack, instruction dispatch, jumps, and function call frames.

### Working prototype

Support integer and boolean values, variables, arithmetic, comparisons, conditions, loops, output, functions, and recursion.

A user should be able to provide a source file, compile it, inspect the generated bytecode, and run it. Invalid programs should produce errors with source locations.

### Distinctive feature

Add an execution debugger that advances one instruction at a time and displays the operand stack, call frames, instruction position, and variable values.

### Demonstration

- Compile and execute factorial and Fibonacci programs.
- Run a loop-based numerical or search example within the supported language features.
- Show nested function calls and recursive call frames.
- Demonstrate syntax errors, undeclared variables, and type mismatches.

### Core CS understanding demonstrated

Compiler design, trees and hash tables, stack-based execution, runtime memory organization, function calling conventions, and programming-language semantics.

### Validation and resume evidence

- Test expression precedence, variable scope, branches, loops, function calls, and recursion.
- Include invalid-program tests and expected diagnostics.
- Measure compilation time, execution time, and bytecode size on documented example programs.
- Report results with the machine, inputs, and measurement method used.

**Possible resume statement, after implementation:** Built a compiler and stack-based virtual machine for a statically typed language, implementing parsing, scope resolution, type checking, bytecode generation, and recursive function execution.

### Initial scope boundary

Exclude classes, garbage collection, concurrency, and native machine-code generation from the first version. Recursion is supported; an explicit depth or resource limit should be defined during planning.

**Relative difficulty:** Medium to high.

**Best fit:** Broad understanding of compiler construction and execution systems.

## 2. Optimizing Compiler with Control-Flow Analysis

### Project idea

Build a compiler for a small language that generates intermediate code, analyzes program flow, and simplifies the code while preserving its defined behavior.

### Fundamentals to implement

- **Compiler front end:** Tokenize, parse, and validate source programs.
- **Intermediate representation:** Generate three-address code with explicit operations and jumps.
- **Basic blocks:** Group instructions that execute sequentially without internal branching.
- **Control-flow graph:** Connect blocks according to possible execution paths.
- **Data-flow analysis:** Repeatedly propagate information until the analysis stops changing.
- **Optimization passes:** Implement constant folding, constant propagation, and dead-code elimination.
- **Liveness analysis:** Determine whether a variable's current value may be needed later.
- **Intermediate-code interpreter:** Execute both original and optimized code.

### Working prototype

Accept integer programs with assignments, output, branches, and loops. Display the original intermediate code, control-flow graph, analysis results, and optimized code.

The user should be able to run both versions on the same input and compare their output and executed instruction counts.

### Distinctive feature

Explain each optimization using the analysis information that justified it. For example, show why a variable is known to hold a constant or why an assignment's value is never used.

### Demonstration

- Reduce constant expressions to computed values.
- Propagate constants through safe assignments and branches.
- Remove assignments whose results are unused when removing them preserves behavior.
- Show cases where an optimization must be withheld because information is uncertain.

### Core CS understanding demonstrated

Compiler design, graph construction and traversal, set operations, fixed-point algorithms, program semantics, and performance analysis.

### Validation and resume evidence

- Test each optimization separately and in combination.
- Compare original and optimized outputs and defined errors across a documented test suite.
- Measure static instruction counts, executed instruction counts, and runtime separately.
- Cover branches, loop-carried values, and operations that may fail.
- Explain why each transformation preserves behavior under the chosen language rules.

Matching outputs on tests are evidence of correctness, not a general proof that every transformation is correct.

**Possible resume statement, after implementation:** Developed an optimizing compiler using control-flow graphs and iterative data-flow analysis, implementing constant propagation, liveness analysis, and dead-code elimination with differential execution tests.

### Initial scope boundary

Start with integers and explicitly defined arithmetic behavior. Exclude pointers, complex aliasing, function side effects, and advanced loop optimizations. Define overflow, division, and observable errors before implementing transformations.

**Relative difficulty:** Medium to high.

**Best fit:** Strong interest in algorithms, program analysis, and performance.

## 3. Static Analyzer Using Abstract Interpretation

### Project idea

Build a tool that detects potential programming errors without executing a program. Use abstract interpretation: track approximate information, such as possible integer ranges, instead of every concrete value.

### Fundamentals to implement

- **Compiler front end:** Parse source programs and perform declaration and type checks.
- **Control-flow graph:** Represent the paths through branches and loops.
- **Definite-assignment analysis:** Determine whether a variable is assigned on every path before a read.
- **Interval analysis:** Track lower and upper bounds for integer values.
- **Transfer functions:** Describe how each statement changes the analysis information.
- **Merge operations:** Combine information from multiple incoming paths conservatively.
- **Worklist algorithm:** Revisit affected blocks until the analysis stabilizes.
- **Loop convergence:** Use an appropriate widening strategy so range analysis terminates.

### Working prototype

Analyze a small integer language with assignments, arithmetic, conditions, and loops. Report reads before assignment, possible division by zero, and provably unreachable branches.

Each diagnostic should identify the source location, explain its reasoning, and distinguish a definite finding from a possible issue where applicable.

### Distinctive feature

Show the information behind each warning. For example: "At this division, the divisor may be between -2 and 3, so zero is possible."

### Demonstration

- Detect a variable assigned on only one branch before it is used.
- Warn when a divisor's range includes zero.
- Show how a condition narrows a variable's possible range.
- Identify a branch that the analysis proves cannot execute.
- Explain a false alarm caused by lost relationships between variables.

### Core CS understanding demonstrated

Compiler design, graph algorithms, discrete mathematics, ordered sets and lattices, fixed-point computation, formal methods, and program correctness.

### Validation and resume evidence

- Create programs with known errors and corresponding corrected versions.
- Record detected errors, missed known errors, and false alarms on that test suite.
- Measure analysis time and worklist iterations.
- Test branches and loops, including loops whose ranges keep expanding.
- Document assumptions and explain why conservative analysis can produce false alarms.

**Possible resume statement, after implementation:** Built a static analyzer using abstract interpretation and worklist-based data-flow analysis to detect uninitialized reads and possible division by zero, with source-level diagnostic explanations.

### Initial scope boundary

Start with one function and integer variables. Exclude pointers, heap objects, concurrency, and analysis across function calls. Define arithmetic behavior and the analysis assumptions in the approved plan.

**Relative difficulty:** High in conceptual depth; manageable with a small language.

**Best fit:** Interest in mathematical reasoning, correctness, and formal methods.

## Original Recommendation Before Topic Selection

Choose the **Small Compiler and Virtual Machine** for the broadest demonstration of core CS understanding and the clearest end-to-end demo.

Choose the **Optimizing Compiler** if algorithms and performance are your main interests. Choose the **Static Analyzer** if you prefer mathematical reasoning and correctness.

For resume and master's preparation, the strength comes from a complete implementation, the ability to explain design choices, and reproducible validation. Add quantitative claims only after measuring them.

## Common Submission Requirements

- Working command-line tool or application with installation and run instructions.
- Source code for the core algorithms and a dependency list.
- Language grammar, supported features, and defined behavior.
- Architecture documentation tracing source input to final output.
- Example programs, expected outputs, and error cases.
- Correctness tests and reproducible measurement scripts where relevant.
- A short report covering design decisions, results, and limitations.
- A demonstration showing valid programs and meaningful failure cases.

A visual interface is optional. The implementation of compiler fundamentals is the primary contribution.

For the selected FlowGuard project, an interactive visual interface is a core proposed requirement. Its input-flow focus differs from the original interval-analysis proposal above.

## Reference Starting Points

- [LLVM: My First Language Frontend](https://llvm.org/docs/tutorial/MyFirstLanguageFrontend/index.html) — a reference for the structure of a small compiler. LLVM integration is not required for these proposals.
- [ANTLR: About the Parser Generator](https://www.antlr.org/about.html) — a reference for grammar-based parser generation. Writing a small parser yourself can make the parsing fundamentals more visible.
