## 1. Purpose and Requirement Categories

FlowGuard connects compiler construction, program analysis, and runtime systems. Users write a small typed program, inspect its compiler artifacts, follow possible unsafe input flows, and optionally execute generated bytecode in a bounded virtual machine.

- **Required behavior (R):** Release obligations based on approved scope, including delegated exact design choices recorded here for review.
- **Implementation choice (IC):** Technical realization selected under the user's approved stack and delegation; defined in the implementation plan, with no unexplained alternatives left for its implementer.
- **Assumption (A):** Unconfirmed delivery information that must not become an invented commitment.
- **Open decision (OD):** Information still unknown. No unresolved architecture/product decision may be hidden in implementation instructions.

This PRD is the single source of truth for product behavior. The separate plan defines implementation. Changes to either approved scope or an approved plan require the user's decision and synchronized state updates.

## 2. Problem, Users, and Value

Compiler concepts are often taught separately. FlowGuard makes the whole process visible: text → tokens → AST → symbols → lowered control-flow graph → taint states/findings → bytecode → optional bounded execution.

Primary users are compiler-design students and evaluators. Secondary users learn how untrusted input reaches sensitive operations. The core contribution is our lexer/parser, type checker, graph lowering, data-flow solver, code generator, bytecode verifier, and VM. Editor/graph libraries support presentation only.

The demo shows an unsafe query, source-linked propagation, a modeled parameter-binding correction, regenerated bytecode, and simulated runtime events. An animation of analysis must be distinguished from actual VM execution.

## 4. Architecture and Component Responsibilities

**IC-01:** Use npm workspaces: `packages/core`, `packages/cli`, `apps/web`. The core has no DOM/Node/filesystem/network dependencies. It is used by analysis workers, execution workers, and CLI adapters. The browser app is served locally; there is no HTTP analysis backend.

Logical modules:

- Source adapter: decode/validate text, create immutable snapshots and line indexes.
- Lexer/parser: tokenize and build source-spanned AST with precedence.
- Semantic checker: resolve stable symbols/scopes, check initialized declarations, types, signatures, and template notices.
- Lowerer: produce typed instruction-level control-flow graph with explicit short-circuit edges and finite temporaries.
- Solver: compute forward may-taint sets to a fixed point.
- Finding/provenance module: inspect final sink-argument states and explain contributing sources with bounded dependency facts.
- Recorder: capture bounded analysis deltas independently of solver completion.
- Code generator/verifier: translate lowered instructions to typed stack bytecode; verify branches, stack states, and slots.
- VM: execute verified bytecode only, using supplied input; return values/events/errors under hard budgets.
- Coordinator: stage sequence, validation, limits, progress, and terminal outcomes.
- Serializer: versioned JSON and readable Markdown using the analyzed snapshot.
- Browser controller: source revision, request/worker identity, stale protection, selections, replay, and separate execution state.
- Presenters: editor, graph, inspectors, findings, bytecode and runtime views.
- CLI: explicit filesystem input/output and terminal exit mapping.

No presentation module computes separate compiler/taint semantics. Visual layout positions are not semantic edges.

## 5. Data Flow and Processing Control

1. Input adapter constructs a snapshot of the exact source; no newline rewriting.
2. Analyze request captures snapshot, revision, request ID, and fixed effective configuration.
3. Coordinator validates → lexes → parses → checks semantics → lowers → solves → builds findings → generates/verifies bytecode → returns one terminal result.
4. Each completed stage may be inspected. A blocking error prevents its dependent stages. Findings are publishable only after analysis converges; bytecode is runnable only after generation/verifier completion.
5. UI accepts messages only for its active request and snapshot revision. Edit/load invalidates active work and source highlights; late messages cannot replace new results.
6. Run uses the verified bytecode from the current successful snapshot, separate supplied inputs, and a fresh execution worker. Analyze never starts execution automatically.
7. VM returns runtime results for that snapshot. Runtime events do not change taint findings or prove security.
8. Export takes an immutable result snapshot. Optional runtime data is included only when identities match; the source in a report is never silently taken from a newer editor revision.

Analysis cancellation terminates/recreates its worker; execution cancellation terminates its separate worker. CLI interruption is a cancelled outcome. Layout and report failures do not destroy otherwise successful analysis.

## 6. Exact Language Rules

The file extension is `.fg`. Source is UTF-8, with an optional leading BOM ignored for lexing while offsets remain unchanged. Identifiers use ASCII letters/underscore followed by ASCII letters/digits/underscore. Reserved words are `let`, `string`, `int`, `bool`, `if`, `else`, `while`, `true`, `false`, `input`, `print`, `sql_query`, `sql_bind`, and `shell`; they cannot be variable names. Strings may contain Unicode; raw line breaks inside strings are invalid.

### 6.1 Grammar and precedence

A program is zero or more statements. Statements are initialized declaration, assignment, built-in effect call, block, conditional, or loop. Declaration syntax is `let name: type = expression;`. Assignment is `name = expression;`. Blocks use braces. `if (expression) block` has an optional `else block`; `while (expression) block` requires a block. Semicolons are mandatory for declarations, assignments, and effect calls. No `break`, `continue`, or empty statement.

Types are `string`, `int`, and `bool`. Literals are double-quoted strings, decimal integers, and `true`/`false`. Parentheses group expressions. Precedence from low to high: `||`, `&&`, equality `== !=`, relational `< <= > >=`, addition `+ -`, multiplication `* / %`, unary `! -`, primary expression. Binary levels associate left; unary associates right. Calls are only the fixed built-ins, not arbitrary functions.

`//` comments end at a newline. `/* ... */` comments do not nest and must terminate. Strings accept `\"`, `\\`, `\n`, `\r`, and `\t`; other escapes produce a lexical error. No interpolation or numeric conversion functions.

### 6.2 Types, scope, and evaluation

- Every declaration has an initializer; it is not in scope during its own initializer.
- No shadowing of any visible name. A name can be reused in disjoint sibling scopes. Duplicate declarations in one scope are invalid.
- Block declarations are inaccessible outside their block. Loop-body declarations are initialized on each iteration.
- Assignment requires a visible declared name and matching type.
- `+` accepts two strings or two integers; other arithmetic requires integers. Relational operators require integers; equality requires matching scalar types. Boolean operators and conditions require booleans. No implicit conversions.
- Binary operands and call arguments evaluate left to right. `&&` evaluates its right operand only when the left is true; `||` only when the left is false.
- Integer literals are 0–2147483647. Unary minus constructs negatives; minimum int can be expressed as `-2147483647 - 1`. Integers outside signed 32-bit range at runtime produce an overflow error rather than wrapping. Division truncates toward zero; remainder follows the dividend's sign. Division/remainder by zero produce runtime errors.
- Runtime arithmetic uses exact widened integer calculation before the 32-bit range check. No JS floating-point multiplication approximation is accepted as the integer semantics.

Whitespace-only source is valid as an empty program in the core/CLI: empty findings and a halt-only bytecode program. The UI shows its empty state and disables Analyze/Run until meaningful source is present. Comment-only source can be analyzed and completes without statements.

### 6.3 Built-ins and template checking

`input(prompt)` is an expression returning `string`; prompt is one string expression. `print(value)`, `sql_query(query)`, `sql_bind(template, value)`, and `shell(command)` are void effects and cannot appear inside value expressions.

- `input`: each syntactic occurrence contributes one stable source ID in static analysis. Runtime consumes the next supplied string in encounter order and records an input event; exhausted input produces a runtime error.
- `print`: accepts one scalar; emits a simulated print event at runtime, not an injection finding.
- `sql_query`: one string; taint in argument 0 yields a possible query-text finding. Runtime only records the query text.
- `sql_bind`: string template and one scalar value; only template taint is a query-text sink. Runtime records template/value separately; it performs no actual binding or SQL execution.
- `shell`: one string; taint in argument 0 yields a possible command-text finding. Runtime only records command text.

A directly literal `sql_bind` template must contain exactly one `?` character; zero/multiple characters are a blocking semantic error. This is an educational character-count rule, not SQL-aware parsing. Every nonliteral template gets a nonblocking `TEMPLATE_UNVERIFIED` notice, even a variable initialized to a literal. Taint analysis continues and still detects tainted templates. The notice never asserts injection or successful format validation.

## 7. Lowering, Static Analysis, and Explanations

### 7.1 Graph and short-circuit behavior

Lower to typed instructions with finite user slots and temporary slots: constant, copy, unary, binary, input, effect, conditional branch, jump, and halt. Every instruction is a CFG node with source mapping. Entry is instruction 0; an empty program contains only halt. Edges are next/true/false/jump/loop-back where applicable; halt is exit.

Nested expressions lower in evaluation order. Logical operators lower to branches assigning a fresh boolean result slot on both paths, followed by a merge; no eager `AND`/`OR` execution is allowed. Loop tests precede bodies; body ends return to the test; false test leads to following code.

Static analysis conservatively follows both structurally reachable branch alternatives, including literal conditions; it does not prove feasibility. Consequently a statically highlighted short-circuit alternative may never execute at runtime. Report this limitation explicitly.

### 7.2 Taint semantics and algorithm

**R-09:** Use a forward may-analysis: a reached state maps slot IDs to sets of syntactic input IDs. Distinguish an unvisited node from a reached node with empty sets. One loop input occurrence always has the same static source ID.

Constants clear their destination set. Copies/unary expressions copy operand contributions. Binary expressions union operand contributions. Input overwrites its destination with its source ID; the prompt's taint does not identify the newly returned source. Conditional branches do not taint assignments solely through control dependence. Effect instructions do not change the environment. Merges union predecessor sets per slot. Slots remain finite across scopes; only visible user symbols are shown as in-scope variables.

Initialize entry as reached with empty sets and all others unvisited. A deterministic FIFO worklist merges reached predecessor outputs, applies transfer rules, and schedules successors when reachability/output changes. Deduplicate queue membership. Complete when the queue is empty. Source sets form a finite lattice and transfers are monotone under inclusion; no widening is needed. Check work/time budgets inside stages.

### 7.3 Findings, provenance, and replay

**R-10:** Evaluate sinks after convergence. Emit one finding per effect-call sensitive argument/rule, containing all contributing source IDs, stable ordering, and source spans. Findings are possible explicit flow, not proven attack paths.

For each contribution record bounded predecessor/assignment dependency facts against final states. Reconstruct an explanation with visited tracking; label merges/cycles rather than walking infinitely or fabricating a single feasible trace. When provenance is capped, retain source sets/findings and mark the explanation incomplete.

**R-11:** Record solver state changes as deltas, with bounded checkpoints, for play/pause/next/previous/reset. Replay is analysis progression, not program execution. A trace cap truncates replay while the solver continues. Replay completeness and analysis completeness are separate fields.

## 8. Code Generation and Virtual Machine

**R-12:** Compile the lowered graph into a versioned typed stack-machine bytecode artifact containing slots, constants, instructions, jumps, and source maps. Display a readable disassembly and include it in reports. It is a custom compiler target, not native machine code.

Instructions cover constants, loads/stores, typed arithmetic/comparison, conditional/unconditional jumps, input, modeled effects, and halt. Branches preserve short-circuit semantics; assignments and each statement boundary leave the operand stack balanced. Type-check/verify all instructions and stack joins before marking the artifact runnable.

**R-13:** Explicit Run executes verified bytecode in a fresh worker. User supplies a JSON array of strings before running; defaults to an empty array. CLI uses an explicitly supplied JSON input file. No interactive blocking prompt is needed. Execution is continuous rather than a separate VM step debugger; analysis replay is the required debugger-like feature.

VM outcomes are completed, runtime-error, cancelled, incomplete-limit, or internal-error. Report consumed input count, final values for top-level variables, bounded events, instruction count, and elapsed time. An error reports code, instruction/source span, and preserved events. Arithmetic/input/limit failures do not rewrite static findings.

Only the custom instruction interpreter executes; never `eval`, generated JavaScript, actual SQL, subprocesses, or shell commands. SQL/shell event messages explicitly say simulated. All event values render as text.

## 9. Data Models and Schema

**R-14:** Use protocol/result schema version `1`, analyzer version `0.1.0`, language version `1`, and bytecode version `1` in the initial implementation. Shared schemas reject unknown versions and invalid discriminated outcomes.

Required models: SourceSnapshot; SourceSpan; Token; ASTNode; Symbol/Scope; TypedSlot; LoweredInstruction/CFGEdge; InputSource; TaintState; Finding/ExplanationFact; ReplayEvent/Checkpoint; BytecodeArtifact; Diagnostic; AnalysisRequest/Progress/Result; ExecutionRequest/Event/Result; ExampleProgram; and EffectiveLimits. Exact fields and validation contracts are fixed in the implementation plan.

Offsets are zero-based UTF-16 code units, end-exclusive. Line/column are one-based with columns in UTF-16 units, matching Monaco. CRLF counts as one line break but two offsets; CR and LF alone are line breaks. Leading BOM occupies its original offset. Source is not normalized. Unicode surrogate pairs inside strings must preserve consistent highlighting.

IDs are deterministic by lexical/preorder/instruction ordering: tokens `tok-N`, AST `ast-N`, symbols `sym-N`, slots `slot-N`, source calls `src-N`, graph nodes `ir-N`. Findings identify rule plus effect AST ID plus argument index. Runtime/request IDs are not semantic artifact IDs.

Reports preserve source snapshot and reference integrity. Runtime and static data remain separate. No database schema/migration is needed: only versioned interchange schemas and user-chosen source/report files.

## 10. APIs, Request/Response Behavior, and Integrations

**R-15:** Analysis API accepts validated source snapshot/options and emits stage progress plus exactly one terminal result. Statuses are completed, invalid-source, invalid-request, cancelled, incomplete-limit, and internal-error. Only completed results carry a security verdict and runnable verified bytecode.

Each message includes request ID/revision. Ignore late/duplicate messages. Source errors have stable codes/spans and completed-stage artifacts only. Worker transport uses serializable plain data; no callbacks, arbitrary filesystem paths, or execution commands are accepted.

Execution API receives bytecode tied to the completed snapshot and bounded input strings. Validate/verifier-check even if a caller bypasses UI controls. Runtime worker errors become internal-error and do not erase the source or successful static result. Editing cancels running analysis/execution, resets replay/selection, and disables Run on stale bytecode.

**R-16:** CLI analyzes an explicit file by default, optionally runs its verified bytecode, and emits JSON or Markdown. stdout contains report only; stderr contains human progress/errors. Exit mapping is defined in the plan. Existing output files require explicit overwrite permission. Reading input files is adapter behavior, not engine filesystem access.

There is no HTTP analysis API, identity provider, database driver, remote analyzer, or runtime telemetry. Local server serves packaged assets only. Dependency installation and CI downloads are separate from local runtime behavior.

## 12. States, Errors, and Fallbacks

**R-18:** Provide distinct initial/empty, running analysis, completed with findings, completed without findings, invalid-source, invalid-request/file, cancelled, incomplete-limit, internal-error, and stale states. Runtime states independently include idle, running, completed, error, cancelled, and incomplete-limit.

- Empty UI offers examples; no finding/graph placeholder suggests a failure.
- Running shows stage text, not an invented percentage. Reject duplicate active requests.
- Completed without findings says “No unsafe flows detected by the supported analysis.” Invalid/cancelled/incomplete outcomes cannot say that.
- Missing artifacts state the unavailable stage/reason. Previous security results never appear as current after an invalid run.
- Source edit removes old source marks, pauses replay, invalidates active worker identity, and marks old immutable results stale. Previous-snapshot export is explicitly labeled.
- Graph layout failure retains findings/inspectors and offers a node/edge list. Large graphs use the same list fallback.
- Replay/provenance truncation does not imply solver failure.
- Export failure leaves analysis intact; success means serialized/download initiated, not proof that the browser saved it permanently.
- Internal failures show a stable diagnostic code and retry guidance, without automatic source logging.
- Runtime errors preserve bounded events and point to the failing instruction/source, without changing static analysis completion.

## 14. Configuration, Performance, and Reliability

**R-20:** The following hard defaults are recorded in reports; no UI/CLI options may increase or disable them in release 1:

- Source: 256 KiB UTF-8; parser nesting: 128; tokens: 65,536; AST nodes: 20,000.
- Lowered CFG: 2,000 nodes; slots: 4,000; input-source occurrences: 256; bytecode: 50,000 instructions.
- Solver: 200,000 processed nodes; bytecode verifier: 200,000 node visits per verification pass; retained in/out state cells at most 4,000,000; retained source-set memberships at most 2,000,000; analysis deadline: 10 seconds across compiler stages.
- Replay: 10,000 delta events; checkpoints every 100 events; trace serialization budget 8 MiB.
- Provenance: 20,000 deduplicated facts overall; explanation display at most 200 facts per finding.
- Structured report: 16 MiB UTF-8; readable report: 16 MiB UTF-8; over-limit export reports an export error, without truncating a supposedly complete report silently.
- Graph rendering: interactive layout at most 200 nodes; larger results use searchable node/edge list.
- VM: 100,000 instructions, 1-second execution deadline, stack depth 1,024, one string at most 64 KiB UTF-8, aggregate UTF-8 string bytes in slots/stack at most 4 MiB, retained event payload at most 1 MiB, at most 1,000 events, supplied input at most 1,000 strings/1 MiB total.

Trace/provenance caps degrade presentation, not solver validity. Token/AST/graph/solver/codegen/time caps yield incomplete-limit, not invalid-source. VM caps yield incomplete-limit with previous events. Invalid input data is invalid-request. A per-stage checkpoint checks time at least every 256 units and at loop boundaries; workers have independent watchdog termination. State-cell/source-membership caps also bound retained solver data; copy-on-write sets must not hide unlimited allocation. Use incremental byte accounting for traces/reports rather than first constructing an unbounded serialization. Allocation counts and serialized-size budgets replace a portable hard browser heap quota; no claim is made of an enforceable OS memory limit.

Performance targets: on the current development Mac with hardware/browser recorded at measurement time, p95 analysis ≤2 seconds for 20 fixtures within 1,000 nonblank lines/500 lowered nodes/50 sources; p95 graph readiness ≤2 seconds for 200 nodes; selection and visible cancellation ≤250 ms. Run each fixture 10 times after one warm-up. CI checks correctness, not hardware-sensitive timings. Limits and targets are fixed; actual Phase 4 measurements and their machine/protocol are recorded in docs/evaluation.md and docs/evidence/benchmark.json, separately from this specification.

Release old results on replacement except the one currently displayed/exported snapshot. Terminate retired workers. Keep one active analysis or VM run per workspace; tabs do not share source. Source sets and slot counts are finite; deduplicate queues/facts, cap traces, and avoid storing full states at every event. No distributed queue or database cache is needed.

## 17. Acceptance Criteria

- **AC-01:** Valid source yields all completed artifacts with intact spans/IDs; empty core/CLI source yields halt-only bytecode.
- **AC-02:** Invalid lexical/grammar/name/type/signature/initializer/template-literal input yields appropriate blocking diagnostics and no completed verdict/runnable bytecode.
- **AC-03:** Direct/transitive/multiple-source sink flow yields one correctly attributed finding per sink argument/rule.
- **AC-04:** Trusted overwrites clear explicit contributions on that path; merges and zero-iteration loops preserve all structural may-flow contributions.
- **AC-05:** Short-circuit IR/bytecode executes operands correctly; conservative static findings explain structural infeasibility limits.
- **AC-06:** Tainted bound value alone creates no query-text finding; tainted template does; nonliteral placeholder uncertainty is nonblocking and labeled.
- **AC-07:** Solver terminates or reports a limit; loops use finite source identities. Provenance/replay never recurse or allocate indefinitely.
- **AC-08:** Source/graph/bytecode selections are consistent; completed replay reaches final states; truncation labels distinguish presentation from analysis completion.
- **AC-09:** UI handles every analysis/runtime/empty/stale/error state and cancellation/race behavior without mixing snapshots.
- **AC-10:** Generated bytecode passes verifier; malformed/type-inconsistent internal artifacts are rejected. Runtime follows exact integer/string/boolean and short-circuit rules.
- **AC-11:** VM input, print, query, bound-query, and command events are deterministic and simulated; no external operations occur. Runtime errors/limits retain preceding events.
- **AC-12:** UI/CLI core outputs match; CLI exits and JSON/Markdown exports match contracts; reports retain the exact analyzed source/version/limits.
- **AC-13:** Save/load protects dirty source; reload has no hidden recovery/history; analysis/runtime never persist/upload source automatically.
- **AC-14:** Hard caps fail with explicit outcomes; graph/layout/export failures preserve usable results; stale results cannot run.
- **AC-15:** Local production assets support the documented clean-install demo and keyboard/reduced-motion/text-label interactions.
- **AC-16:** Approved performance targets have recorded measurements or an explicit user-approved revision; no planned result is called executed evidence.
- **AC-17:** GitHub Actions passes checks on real commits; no license file is added; reports/README describe actual completed scope.

All R-01–22 must map to tests or demonstration evidence in the implementation plan. Passing a subset does not authorize a release claim for untested requirements.
